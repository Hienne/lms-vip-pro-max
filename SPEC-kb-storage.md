# Spec: `kb-storage` (backend, Phase 1)

Map: [SPEC.md](SPEC.md). Repo: `corebanking-academy`, branch `feat/ai-assistant-rag`.

## Objective

Give the knowledge base its tables, its configuration and one client for the local model, so that
`kb-ingestion` and `kb-chat` build on them. Nothing user-facing ships in this module alone.

## Tech stack

Spring Boot 3.5.16, Java 21 runtime (compiler target 17), Spring Data JPA (`ddl-auto=validate`), PostgreSQL
16 + pgvector (`pgvector/pgvector:pg16`), Spring `RestClient`. No new dependency in this module.

## Schema: `docs/sql/learning_hub_knowledge.sql`

Same style as `learning_hub_learning.sql`: one transaction, no FK/REFERENCES, no DROP, Vietnamese
`COMMENT ON` for every table and column, run once by hand after the identity and learning scripts.

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE learning_hub.knowledge_documents (
    document_id   bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    uploaded_by   varchar(20)  NOT NULL,          -- users.user_id (logical reference)
    file_name     varchar(255) NOT NULL,          -- original name, display only
    mime_type     varchar(100) NOT NULL,          -- detected, not the client's claim
    size_bytes    bigint       NOT NULL,
    storage_key   varchar(100) NOT NULL,          -- UUID file name under app.knowledge.storage-dir
    status        varchar(20)  NOT NULL CHECK (status IN ('queued', 'processing', 'ready', 'failed')),
    error_message varchar(500),                   -- Vietnamese, shown to users when failed
    page_count    integer,                        -- PDF only
    chunk_count   integer      NOT NULL DEFAULT 0,
    attempts      integer      NOT NULL DEFAULT 0,
    create_time   timestamptz  NOT NULL DEFAULT now(),
    started_at    timestamptz,
    processed_at  timestamptz                     -- set when ready or failed
);
CREATE INDEX idx_knowledge_documents_queue    ON learning_hub.knowledge_documents(status, create_time);
CREATE INDEX idx_knowledge_documents_uploader ON learning_hub.knowledge_documents(uploaded_by, create_time DESC);
CREATE INDEX idx_knowledge_documents_created  ON learning_hub.knowledge_documents(create_time DESC);

CREATE TABLE learning_hub.knowledge_document_chunks (
    chunk_id       bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    document_id    bigint       NOT NULL,         -- knowledge_documents.document_id (logical)
    chunk_index    integer      NOT NULL,         -- 0-based order inside the document
    content        text         NOT NULL,
    page_number    integer,                       -- null for .md and .docx
    line_start     integer      NOT NULL,
    line_end       integer      NOT NULL,
    token_estimate integer      NOT NULL,
    embedding      vector(1024) NOT NULL          -- bge-m3, L2-normalised by Ollama
);
CREATE UNIQUE INDEX uq_knowledge_chunks_document ON learning_hub.knowledge_document_chunks(document_id, chunk_index);
CREATE INDEX idx_knowledge_chunks_embedding ON learning_hub.knowledge_document_chunks
    USING hnsw (embedding vector_cosine_ops);
```

Naming follows the backend's conventions, mapped from the request: `id` → `document_id`,
`uploaded_by_user_id` → `uploaded_by` (like `learning_assets.uploaded_by`), `size` → `size_bytes`,
`error` → `error_message`, `created_at` → `create_time`; tables are prefixed `knowledge_` inside the shared
`learning_hub` schema. `processed_at` keeps the guideline's meaning (when the job finished).

Chunks of a document are inserted in the same transaction that sets it `ready`, so a search never sees a
half-processed document.

**`AI_ASSISTANT` function** (D3), in `learning_hub_identity.sql` (the single source for identity seed):
`('AI_ASSISTANT', 'Trợ lý AI', '/assistant', 155)`, granted to `LEARNER`, `INSTRUCTOR`, `ADMIN`,
`SUPER_ADMIN` and `REPORT_VIEWER`. `docs/sql/README.md` lists the new script and the run order.

## Configuration (`application.yml`, env overrides, nothing hard-coded in Java)

```yaml
app:
  knowledge:
    storage-dir: ${KNOWLEDGE_STORAGE_DIR:./data/knowledge}
    max-file-size: ${KNOWLEDGE_MAX_FILE_SIZE:20MB}
    worker:
      poll-interval: ${KNOWLEDGE_WORKER_POLL:2s}
      concurrency: ${KNOWLEDGE_WORKER_CONCURRENCY:1}
      max-attempts: 3
    chunk: { target-tokens: 600, max-tokens: 800, overlap-tokens: 80 }
    retrieval: { top-k: 5, min-similarity: 0.35 }
    ollama:
      base-url: ${OLLAMA_BASE_URL:http://localhost:11434}
      chat-model: ${OLLAMA_CHAT_MODEL:qwen3:8b}
      embed-model: ${OLLAMA_EMBED_MODEL:bge-m3}
      connect-timeout: 5s
      read-timeout: 180s
      keep-alive: 10m
```

Bound to `KnowledgeProperties` (`@ConfigurationProperties("app.knowledge")`, validated at startup).

## `OllamaClient` (`knowledge.ai`)

One concrete Spring bean over `RestClient` (no interface; tests replace it with `@MockitoBean`):

| Method                                                      | Ollama API                      | Notes                                                     |
| ----------------------------------------------------------- | ------------------------------- | --------------------------------------------------------- |
| `boolean isAvailable()`                                     | `GET /api/version`              | 2 s timeout; never throws                                 |
| `List<float[]> embed(List<String> inputs)`                  | `POST /api/embed`               | batches of 16; checks every vector has 1024 dimensions    |
| `String chat(List<Message>, Options)`                       | `POST /api/chat` `stream:false` | `think:false`, `temperature 0.1`, `num_ctx 8192`          |
| `void chatStream(List<Message>, Options, Consumer<String>)` | `POST /api/chat` `stream:true`  | reads NDJSON lines, forwards each `message.content` delta |

Connection refused or timeout throws `OllamaUnavailableException` (transient); any other non-2xx throws
`OllamaException`. The client never logs prompts or document text (guideline §8), only model, duration and
sizes.

`DocumentChunkRepository` uses `JdbcTemplate` because JPA does not map `vector`: batch insert with
`CAST(? AS vector)` and the native search in `kb-chat`. The class comment says why.

## Testing

- `KnowledgeSchemaIT` (Testcontainers `pgvector/pgvector:pg16`, runs the three SQL files): the app context
  starts with `ddl-auto=validate`; the HNSW index exists; a 1024-dim insert and a cosine query work.
- `OllamaClientTest` (`MockRestServiceServer`): request bodies (`think:false`, model names from config),
  1024-dim check, connection refused → `OllamaUnavailableException`.

## Boundaries

- Always: SQL file run by hand, `ddl-auto=validate` and Flyway off unchanged.
- Ask first: any other dependency; a change to the global multipart limit (stays 500MB; the 20 MB rule is
  enforced in the service).
- Never: run SQL at startup; add FKs; touch the remote database.

## Success criteria

The three SQL files load into a fresh `pgvector/pgvector:pg16`; the app starts against it; `/auth/me` of
every seeded role lists `AI_ASSISTANT`; the two test classes pass in `mvn clean verify`.
